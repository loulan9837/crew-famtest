# 数据持久化与自动备份 · 方案与需求说明

> **文档用途**：在 **R2 + 远程 Postgres（如 Neon）** 前提下，定义自动备份的需求边界、单次 run 成功口径、一致性、manifest、调度、安全、保留、防灾与演练，避免「裂脑恢复」「半套 run 标成功」「休眠不备份」「坏备份覆盖好备份」等风险。  
> **职责边界**：本文**仅**规范 Postgres 与 R2 的 **冷备、恢复与合规**；**不定义** 项目记忆如何被 Agent 消费、生成用例时上下文如何拼装、或 Agent 知识库何时重建。后者见 `docs/项目记忆持久化与Agent读取策略.md`。**有定时冷备 ≠ 业务上记忆已正确注入或 Agent 已单次读完。**  
> **前提**：暂不考虑多用户；预估总数据量 ≤1GB。  
> **更新时间**：2026-04-02（修订：职责拆分与交叉引用）

## 〇、适用范围与部署边界

| 部署形态 | 是否适用本文 |
|----------|----------------|
| **云端**：Streamlit Community Cloud + 远程 Postgres + R2 | **适用**（目标形态） |
| **本地 / JSON 文件后端 / 本地 Sqlite** | **不适用**本期方案；另用操作系统级文件备份或单独文档说明，**不得**与本文混验收 |

**双项目（`FAMBASE` / `RM11`）**：本期备份与恢复单元为 **整库 + 与本次 run manifest 绑定的 R2 前缀/对象集合**（见第二节）；**不按 `project_id` 单独导出/恢复**。若未来需要按项目恢复，需另起「备份分区策略」文档。应用层仍须保证记忆与导入数据按 `project_id` / `current_project` 隔离（见 `项目记忆持久化与Agent读取策略.md`），与「整库冷备」分工不同。

## 一、需求内容摘要

1. **背景**：Streamlit Community Cloud **无可靠本地持久盘**；项目记忆、设计图/回归用例等依赖 **Postgres（元数据与可检索内容）** 与 **R2（对象存储）**。
2. **目标**：按固定周期 **自动** 生成可带走的备份，并在灾难或误操作后可恢复；备份访问受控、可审计。
3. **非目标（本期）**：不承诺数据库厂商控制台里的 **连续 WAL 级 PITR**（见第六节），除非单独采购/开启对应托管能力并另起文档。  
4. **非本文范围**：Agent 读取契约、记忆制品写入触发、设计图「最新」的 DB 排序准则、全回归导入后是否自动/手动刷新知识库等业务规则——见 `docs/项目记忆持久化与Agent读取策略.md` 与 `docs/Agent知识库-PRD.md`。

## 二、单次 backup run：成功定义、状态机与 manifest（实现最易踩坑）

### 2.1 Run 成功 = 原子口径（写死）

**一次 `backup_run_id` 仅当以下全部满足时，才视为「成功 completed」：**

1. **Postgres**：`pg_dump`（或等价）产物已上传 R2，且 **校验通过**（大小 + hash 与本地一致）。
2. **R2 业务对象**：按本期策略完成 **清单 manifest 与/或对象世代拷贝**（见 2.3），且 **校验通过**。
3. **总 manifest**（见 2.3）已写入 R2，且内容可被独立校验（hash、必填字段齐全）。

**任一步失败**：

- Run 状态为 **`failed`**（或 **`partial`** 仅用于内部诊断，**禁止**对外等价于成功）；
- **不得**将本次 run 标为「最新可用备份」；
- **不得**执行 **淘汰旧世代**（删除/降级旧备份）；
- **不得**更新任何「指向最新好备份」的指针（若有）。

可选内部状态机（实现建议，非强制命名）：`started` → `pg_ok` → `r2_ok` → `manifest_written` → `verified` → `completed`；任一步失败 → `failed`，并记录失败步骤与原因（**脱敏**，见第八节）。

### 2.2 禁止「半套成功」

同一 `backup_run_id` 下若出现 **Postgres 成功、R2 失败**（或相反），**不允许**：

- 将淘汰逻辑绑定到该 run；
- 在监控/看板上仅因「dump 已上传」显示绿灯；
- 运维按「习惯命名」误选 dump 而无对应 R2 包。

### 2.3 备份包清单（manifest）——恢复单元

**每个 `backup_run_id` 必须对应唯一一份 JSON manifest**（存 R2，例如 `backups/manifests/{backup_run_id}.json`），恢复 Runbook **第一步**为：**校验 manifest 完整性与签名/hash**，再按 manifest 定位对象。

**Manifest 建议必填字段**：

| 字段 | 说明 |
|------|------|
| `backup_run_id` | UUID 或 `YYYYMMDDTHHmmssZ` + 随机后缀 |
| `schema_version` | manifest 格式版本号，便于演进 |
| `created_at_utc` | manifest 最终定稿时间 |
| `postgres` | `{ "object_key": "...", "sha256": "...", "size_bytes": N, "completed_at_utc": "..." }` |
| `r2_dataset` | `{ "mode": "prefix_copy" \| "manifest_only", "prefix_or_keys": [...], "object_count": N, "completed_at_utc": "..." }` |
| `steps` | 各步骤完成时间与状态（`pg` / `r2` / `verify`） |
| `deployment` | 如 `env: prod`，`db_host` **禁止写凭证**，仅写非敏感标识 |
| `notes` | 可选：Neon branch 名、工具版本 |

**原则**：恢复时 **dump + R2 数据集 + manifest 三位一体**；仅靠文件命名约定 **不足**。

## 三、一致性基准与「裂脑」处理（核心）

### 3.1 问题定义

Postgres 导出与 R2 列举/拷贝 **不可能同一物理时刻完成**，存在时间差；期间业务持续写入可能导致：

- **幽灵对象**：R2 有文件，Postgres 无记录；
- **悬空记录**：Postgres 有 `object_key`，R2 无对象。

### 3.2 一致性基准（本期写死）

1. **逻辑基准**：以 **本次成功 run 所恢复的 Postgres 内容** 为索引基准（与 manifest 绑定）。
2. **软一致窗口**：接受单次 run 内 PG 与 R2 两步之间存在 **分钟级** 交叉不一致；恢复后通过 **调和** 收敛。
3. **`pg_dump` 与业务并发**：PostgreSQL 在常规 `pg_dump` 下对导出数据提供 **某一时刻起的一致性快照语义**（以官方与 Neon 文档为准）；**不等于** R2 侧在同一时刻冻结。**本期**接受「PG 为逻辑基准 + 短窗口交叉不一致」；若未来要收紧，需 **维护窗口** 或托管侧 **分支/只读快照 API**（升级为第六节 L2 或单独「强一致备份」能力）。

### 3.3 恢复后调和（Reconciliation）

- **默认策略**：对「无 DB 引用」的 R2 对象 → **移入 `quarantine/` 前缀或生成报告**，**默认禁止自动物理删除**；需 **人工确认** 或双签后删除（与「回滚生产」场景冲突风险见 3.4）。
- 对 DB 中 **GET 404** 的记录 → 标记 `missing_object` / 审计表；业务路径 **禁止** 静默成功。
- **恢复场景须注明「以谁为准」**（见 3.4）。

### 3.4 回滚场景：避免误删仍在线上桶中的合法新对象

若操作是 **将 Postgres 回滚到历史备份**，而 **生产 R2 仍保留较新对象**，则「以恢复后的旧库为准删幽灵」可能 **误伤** 仍被线上引用的对象。

**需求写死**：

- **冷备恢复 / 整站回滚**：明确接受 **恢复点之后 R2 新增对象可能丢失或与旧库不一致**；调和前必须 **冻结写入或切换桶/前缀**，按 Runbook 执行。
- **仅修复裂脑、生产库未回滚**：以 **当前生产 Postgres** 为准调和 R2，**不得**用历史库对当前桶做删除。

### 3.5 验收口径

恢复演练中制造「桶多文件 / 库多悬空行」两种情形，按场景执行调和后，系统状态符合预期且无未处理 404。

## 四、调度方式：禁止应用内定时，必须用外挂调度

### 4.1 约束

- Streamlit Community Cloud **会休眠**；应用内 `schedule` / `APScheduler` **不得**作为备份触发源。
- **不推荐** Webhook 唤醒 Streamlit 再调备份 API 作为主方案。

### 4.2 执行模型

备份由 **与 Streamlit 无关** 的任务触发，**直连** Postgres（备份专用连接）与 R2。

**推荐默认**：**GitHub Actions `schedule`**，密钥用 **GitHub Secrets**。

**备选**：VPS `cron`、独立 Worker（仍不经 Streamlit）。

### 4.3 Postgres 连接：备份与 App 分离

- **应用运行时**可使用 Pooler 连接串（短请求）。
- **`pg_dump` 长任务**：使用 **直连或非池化端点**（以 **Neon 官方文档**为准）；**禁止**默认沿用「仅适合 App」的 Pooler 串导致 dump 中断或隐性限制。
- 文档与 Secrets 中应区分：`DATABASE_URL_APP` vs `DATABASE_URL_BACKUP`（或等价命名）。

### 4.4 GitHub Actions：密钥、权限与供应链

| 要求 | 说明 |
|------|------|
| Workflow 触发 | 备份 workflow **仅**在 `default` 分支（或明确列出的受保护分支）上执行 `schedule` / `workflow_dispatch`；**禁止**未审查 PR 执行带 Secrets 的 workflow |
| 权限最小化 | `permissions` 收紧（如 `contents: read`）；不需要的 `write` 一律关闭 |
| R2 凭证 | 专用 IAM/Token：**仅**允许 `PutObject`/`GetObject`/`HeadObject`/`ListBucket` 在 **`backups/` 前缀**（或独立备份桶）；**禁止**整桶无前缀高权限 |
| 轮换 | Access Key 定期轮换；失效时间可配置 |
| 日志 | **禁止** `echo` 打印连接串、Secret、完整路径中的密钥片段；失败日志 **脱敏** |

### 4.5 Runner 资源、超时与降级

- `pg_dump` + 压缩 + 上传 + 全量 hash 可能触发 **job 超时或 OOM**（尤其接近 1GB）。
- 方案中需定义：
  - **job 超时**（大于默认时显式上调）；
  - 若单次 dump 超过阈值 **X MB**（可配置）或连续失败，则 **切换到自建 Runner / VPS** 执行同套脚本。
- **Artifacts**：若使用 Actions artifact，必须 **私有**、短期保留，不得公开下载链接。

## 五、备份生命周期与保留策略（Retention）

| 参数 | 建议默认值（≤1GB） | 说明 |
|------|---------------------|------|
| Postgres 全量频率 | 每日 1 次 | 可调低 |
| R2 数据集 | 与 PG 同成功 run | 降低裂脑窗口 |
| 最少保留世代 | ≥7（日备）或 ≥4（周备） | 防坏备份覆盖唯一好备份 |
| 最长保留期 | 如 30 天 | 与合规联动见第八节 |
| 淘汰 | **仅**在 run `completed` 且 manifest 已验证后 | 失败 run **不触发**淘汰 |

## 六、时间点恢复（PITR）能力分级

| 级别 | 能力 | 本期是否承诺 |
|------|------|----------------|
| **L1：离线全量快照** | 恢复到 **某一成功 `backup_run_id`** | **承诺**（多世代 + manifest） |
| **L2：任意时刻 PITR** | 如「昨天下午 3:15」 | **不默认承诺** |

**RPO（本期可宣传口径）**：≈ **备份周期 + 软一致窗口**（由 manifest 中各步时间戳界定）。  
**RTO（目标）**：需在 Runbook 中写 **目标耗时**（如「4 小时内完成恢复到 staging 可读」）；每季度演练后修订。

## 七、防灾装甲（实现门禁）

### 7.1 先写后删（Write-then-Delete）

仅当 manifest 进入 **`verified`** 且整 run **`completed`** 后，才允许淘汰超出保留策略的旧对象。

### 7.2 校验（Checksum）

上传后对 R2 对象做 **HEAD/GET** 与本地 hash 比对；失败则 **不淘汰**、run `failed`。

### 7.3 体积跌落熔断（Size Drop Circuit Breaker）

- 新 Postgres dump 相对 **上一份已验证成功** 的 dump，体积下降超过阈值（默认 **30%**，可配置）→ **阻断淘汰**、**不**将本次标为最新好备份、**严重告警**。
- **误杀防护**：合法大批量删数、清库、归档会导致体积正常大跌。必须支持：
  - **人工确认 override**（写入审计日志：操作者、时间、原因、`backup_run_id`）；或
  - **白名单 run**（如关联变更工单号）；  
  避免自动化 **永久卡死** 且无审计。

### 7.4 多世代保留

严禁长期仅保留「最新一份」自动备份。

### 7.5 R2 对象备份

新 manifest / 前缀拷贝 **校验通过后** 才允许删旧世代；**对象数量暴跌熔断** 可与 PG 共用告警通道。

## 八、安全、合规与备份即「第二份生产数据」

| 主题 | 要求 |
|------|------|
| 访问 | 备份对象 **默认私有**；**禁止**匿名 `public-read` |
| 加密 | 启用 **服务端加密**（R2/S3 兼容 SSE 或平台等价能力）；敏感场景可增加上传前客户端加密（另评） |
| 恢复下载 | **短期预签名 URL** 或 IAM 控制；禁止长期公开 URL |
| CI | 见 4.4；artifact 仅内部可见 |
| 调和与删除 | 默认 **quarantine + 人工确认**；文档化 **从 quarantine 回滚** 的步骤 |
| 合规 / 被遗忘权 | 备份含需求、用例、设计描述等；**本期默认**：按 **桶级保留策略** 到期删除整份备份对象；**不**承诺按单条用户记录精确抹除全历史备份（若未来强制要求，需单独 PRD 与工程评估）。用户主动删除业务数据时，是否同步删除已生成备份 **需产品单独拍板** |

## 九、恢复、切流与演练

### 9.1 Runbook（修订顺序）

1. **读取并校验** `backup_run_id` 对应 **manifest**（hash、必填字段）。  
2. 按 manifest 拉取 **Postgres dump**；`pg_restore` 到 **空库或 Neon branch**（**非**直接覆盖生产）。  
3. **只读校验**：抽样查询、关键表行数、与熔断基线对比。  
4. **调和**：按第三节场景选择「以谁为准」，执行 quarantine/标记。  
5. **切流**：仅在验证通过后 **切换应用连接串** 或 **提升 branch 为生产**（蓝绿/一次性切换）；禁止半恢复状态对线上读写。  
6. 冒烟：导入历史、对象 GET、Agent 读取无未处理 404。

### 9.2 演练

- **频率**：每季度至少 **1 次** 在 **staging** 全链路恢复 + 调和验证。  
- **记录**：RTO 实测、问题清单、manifest 版本兼容性。

## 十一、漏洞与对策总览（速查）

| 风险 | 本期硬性要求 |
|------|----------------|
| 裂脑 | manifest 绑定 PG+R2；恢复后调和；区分回滚 vs 仅修裂脑 |
| 半套 run 标成功 | 仅 `completed` 可淘汰；失败不删旧世代 |
| Streamlit 休眠 | 外挂调度，直连 DB+R2 |
| 保留爆炸 | 多世代 + 最长保留 + 仅成功 run 淘汰 |
| PITR 混谈 | L1/L2 分级；RPO/RTO 写清 |
| 坏备份覆盖 | 写后删 + 校验 + 体积熔断 + **override 审计** |
| Pooler 误用 dump | 备份专用直连串，与 App 分离 |
| 供应链/密钥 | workflow 权限、前缀最小权限、轮换、日志脱敏 |

# 用例补充（增量生成）· 产品需求文档

> **文档用途**：在现有「生成用例」主流程基础上，增加一个针对小范围需求变更的**用例补充（增量生成）**能力，避免每次 PRD 小改动都整表重跑，且不破坏现有用例编号与表头规范。
>
> **关联文档**：`四Agent提示词与任务编排-规格说明.md`、`.cursor/rules/project-standards.mdc`、`agent_knowledge-PRD.md`

---

## 一、背景与目标

### 1.1 背景

- 现状：用户基于一版 PRD 通过“四 Agent 流水线”生成一整张用例表，导出为 Excel。
- 实际场景：PRD 经常发生**小范围增补/修订**（例如：
  - 新增断网场景；
  - 增加边界值约束；
  - 调整个别参数范围）。
- 痛点：
  - 每次小改动都重新跑一次完整四 Agent 流程成本高；
  - 人工补充用例容易遗漏极端场景且难以保证 ID 连续性与格式统一。

### 1.2 目标

| 目标 | 说明 |
|------|------|
| 提供增量生成入口 | 在生成用例结果页，提供一个「用例补充（增量生成）」区块，允许用户手动输入“需求修改/补充说明”，由 Agent 在理解**原始需求 + 上次生成的用例**的基础上，只为这部分变更产出增量用例 |
| 严格 Delta 输出 | 基于原始 PRD + 现有用例 + 补充指令，**只输出新增场景**，禁止重写整表 |
| ID 连续且不冲突 | 新增用例的 ID 从 Python 计算的下一个序号开始，连续且不与旧用例冲突 |
| Schema 稳定 | 增量用例表的表头必须与基线表完全一致，避免对 Excel 导出逻辑产生破坏 |
| 合并与导出可控 | 用户先 Review 增量表，可选择「合并至总用例库」或「仅导出本次增量」，避免对历史用例造成误操作 |

## 二、用户场景与交互流程

### 2.1 使用前提

- 用户已通过主流程成功生成一版用例表；
- 页面上存在 `current_cases_df`（当前用例表 DataFrame）；
- 仅在该前提下渲染“用例补充”入口。

### 2.2 用户操作路径

1. **进入生成结果页**
   - 用户执行完一次“生成测试用例”后，在页面下方看到“当前用例表格”以及新的「用例补充（增量生成）」区域。

2. **输入补充指令**
   - 在“补充说明/变更描述”文本域中，输入自然语言指令，例如：
     - 「需求变更：在断网场景下，增加保存草稿的离线缓存校验逻辑」
     - 「新增支付失败重试次数上限为3的场景，并对超过上限的行为做提示」

3. **点击【生成补充用例】**
   - 系统调用**增量 Agent**：
     - 入参包括：原始 PRD 文本、当前基线用例表（Markdown）、用户补充指令、下一可用 ID 序列。
   - 调用成功后，UI 展示一张**增量用例表**（仅包含新增场景），记为 `delta_cases_df`。
   - 若生成失败（如表头不合法、LLM 返回空），在 UI 显示错误信息，用户可修改指令重试。

4. **Review 增量用例**
   - 用户在页面上只看到新增几条用例：
     - 支持按 DataFrame 形式预览；
     - 可滚动查看完整列信息（ID / 模块 / 测试项 / 优先级 / 前置条件 / 操作步骤 / 预期结果）。

5. **决定是否合并**
   - 若不满意本次增量：
     - 点击【丢弃本次增量】，清空 `delta_cases_df`，重新编辑指令再生成。
   - 若确认新增用例合理：
     - 点击【合并至总用例库】：
       - 系统对 `delta_cases_df` 做 Schema 与 ID 合法性校验；
       - 校验通过后，将增量用例合并入总用例表，刷新 `current_cases_df`，并清空 `delta_cases_df`；
       - 合并失败则提示错误原因，不做任何持久化修改。

6. **导出本次增量或更新后的用例**
   - 用户在 Review 增量用例后，有两种导出方式：
     - 【导出补充用例为 Excel】：仅将 `delta_cases_df` 导出为一个单独的 Excel 文件，文件名建议为「{原用例标题}-增量补充-时间戳.xlsx」，方便单独评审或交给其他团队补充；
     - 【合并并导出全量用例】：先执行合并，再按现有逻辑导出包含新老用例的完整 Excel。
   - 两种导出方式都必须沿用现有 Excel 安全与排版规则（单元格换行、防公式注入等）。

## 三、状态与数据结构

### 3.1 关键状态（st.session_state）

| 字段 | 类型 | 说明 |
|------|------|------|
| `current_cases_df` | DataFrame | 当前页面展示和导出的“总用例表”，主流程已有 |
| `base_cases_df` | DataFrame | 本轮增量前的基线用例表快照，用于计算下一 ID 序号与回退 |
| `delta_cases_df` | DataFrame 或 None | 本次补充指令生成的增量用例表，默认 None |
| `incremental_last_instruction` | str | 最近一次补充指令文本，用于回显 |
| `incremental_last_error` | str | 最近一次增量生成错误信息（可选，用于 UI 友好提示） |

### 3.2 状态流转

- **初始态**：`current_cases_df` 存在，`delta_cases_df is None`：
  - 展示补充指令输入框 + 【生成补充用例】按钮；
  - 不展示增量表与合并按钮。
- **生成成功态**：`delta_cases_df` 为非空 DataFrame：
  - 展示增量用例表；
  - 展示【合并至总用例库】与【丢弃本次增量】按钮；
  - 禁止重复点击【生成补充用例】（避免状态混乱），或覆盖生成前清空旧增量。
- **合并完成态**：
  - `current_cases_df` 更新；
  - `base_cases_df` 与 `current_cases_df` 同步；
  - `delta_cases_df` 重置为 None，回到初始态。

## 四、增量 Agent 职责与输出规范

> 增量 Agent 不走完整四 Agent 流程，而是一个独立的小链路。其 Prompt 设计必须继承项目统一规范。

### 4.1 角色设定

- 你是一位资深高级全栈测试开发专家。
- 你已拥有：
  - 《原始需求》全文；
  - 《现有测试用例》表格；
  - 用户提供的《增量指令》；
  - Python 注入的下一可用 ID 起始值。
- 你的唯一任务：**在不破坏现有用例逻辑的前提下，为新增或变更部分补充测试用例**。

### 4.2 表格与排版规范（继承项目铁律）

- 输出格式：**必须为 Markdown 表格**。
- 表头严格固定为（顺序一致）：
  - `ID | 模块 | 测试项 | 优先级 | 前置条件 | 操作步骤 | 预期结果`
- 排版规则：
  - 中英/数字边界**不得出现空格**：例如 `点击Save按钮`。
  - 英文内部保留原始空格。
  - 预期结果**绝对去动词化**：不得出现“点击”“查看”等动作词，仅描述状态/展示/置灰等。
  - 多条预期结果时，必须分行并使用 `1. 2.` 编号；单条时禁止前置编号。

### 4.3 逻辑校验与增量原则

- **纯增量输出**：
  - 必须显式对比《现有测试用例》，严禁重复已有场景；
  - 不得重新输出任何已经存在的用例，无论文字是否完全一致。
- **逻辑推演**：
  - 针对增量指令描述的新逻辑，必须：
    - 覆盖 Happy Path 与关键异常路径；
    - 覆盖断网、杀进程、边界值等极端场景；
    - 考虑新逻辑对既有流程（例如充值/送礼/直播）的潜在回归风险。
- **冲突校验（回归防护）**：
  - 若发现增量指令引入的新行为与原用例中已有行为存在冲突（例如：
    - 新逻辑要求弹窗提示；
    - 老逻辑要求静默处理），
  - 必须补充“回归/冲突验证用例”，明确验证新旧逻辑在关键场景下如何取舍或升级。

### 4.4 ID 强继承

- 增量 Agent 不得自行决定 ID 起始值：
  - Python 侧会注入一个变量 `NEXT_ID_START`（例如：`LIV-0046`）。
  - 你产出的**第一条用例**的 ID 必须严格为 `NEXT_ID_START`；
  - 后续用例 ID 必须在数字部分上递增 1（`LIV-0047`、`LIV-0048` ...）。
- 若增量逻辑需要跨多个模块（如支付 + 直播），由 Python 端控制前缀与序列拆分；当前版本优先保证**单模块内的连续性**。

## 五、架构级漏洞与防御要求（面向开发）

> 以下为本功能在评审阶段识别出的关键风险，开发实现时必须有对应防御逻辑。

### 5.1 漏洞 1：ID 编号断层与冲突

- 隐患：
  - 大模型无状态记忆，容易从 `XXX-001` 重新开始编号；
  - 一旦合并入库，会产生 ID 冲突或断层，影响后续追踪。
- 防御要求：
  - 绝对禁止让大模型自行决定起始 ID；
  - Python 必须扫描基线表的 ID 列，提取数字部分计算最大值；
  - 将 `NEXT_ID_START` 注入 Prompt，并在增量引擎中对生成结果做 ID 合法性校验；
  - 若校验不通过，直接视为生成失败，禁止合并。

### 5.2 漏洞 2：表头 Schema 漂移

- 隐患：
  - 大模型可能省略某些列或调整列顺序；
  - 合并时 Pandas 自动对齐产生 NaN，进而破坏 Excel 导出逻辑。
- 防御要求：
  - 合并前必须严格比较列名列表是否与基线表完全一致（包含顺序）；
  - 不一致时直接抛错，不做任何合并；
  - UI 层用 `st.error` 友好提示，并建议重新生成。

### 5.3 漏洞 3：注意力偏移导致重写全局

- 隐患：
  - 当 PRD 与既有用例内容过长时，大模型可能忽略最后的增量指令；
  - 输出内容变成对原表的“再总结”，而非真正的 Delta。
- 防御要求：
  - Prompt 结构必须将《增量指令 + 起始 ID 要求》放在**最末尾**（Recency Effect）；
  - System Prompt 中必须高亮强调：
    - 「你的唯一任务是输出【增量/Delta】部分，绝对不允许输出已有用例！」；
  - 可在增量引擎中增加简单的重复检测（如与基线用例进行测试项+操作步骤的重复比对）作为兜底。

### 5.4 漏洞 4：新老逻辑冲突

- 隐患：
  - 用户的增量指令与原需求/原用例逻辑存在互斥关系（如静默 vs 弹窗）；
  - 若只补新场景，不回顾旧逻辑，可能造成隐性回归风险。
- 防御要求：
  - Prompt 中明确要求 Agent 做**冲突识别**与**回归用例补充**：
    - 对发现的冲突，必须通过新增回归用例显式验证“新行为在关键场景下是否覆盖旧行为”；
  - 后续可在主流程的用例审查环节加入“冲突标记”列（当前版本先只在内容层体现）。

## 六、验收标准

| 编号 | 验收项 |
|------|--------|
| AC1 | 在已有用例结果页，仅当存在 `current_cases_df` 时展示“用例补充（增量生成）”区域 |
| AC2 | 用户输入补充指令并点击【生成补充用例】，成功产出一张仅包含新增场景的增量用例表 |
| AC3 | 增量用例表的表头与基线表完全一致（列名与顺序都一致），否则前端报错，不允许合并 |
| AC4 | 增量用例 ID 从 Python 计算的 `NEXT_ID_START` 开始，递增且不与基线冲突 |
| AC5 | 用户点击【合并至总用例库】后，新的总用例表包含增量用例且旧用例不变，导出 Excel 正常 |
| AC6 | 在大模型返回异常（空表/非表格）或 Schema/ID 校验失败时，系统以 `st.error` 形式提示且不修改任何已有用例 |
| AC7 | 多次增量生成与合并后，用例表仍保持 ID 连续、Schema 稳定，无 Excel 导出异常 |

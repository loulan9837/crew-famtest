# 用例补充·表头兼容与补充需求无格式限制 · 开发实施文档

> **文档用途**：面向开发Agent，提供表头兼容与补充需求无格式限制的完整技术实施方案。
>
> **关联PRD**：`用例补充-表头兼容-PRD.md`
>
> **关联代码**：`crew_test.py` 中 `generate_incremental_cases` 函数

---

## 一、修改范围

仅修改 `crew_test.py` 中的 `generate_incremental_cases` 函数，不涉及 `app_ui.py` 及其他模块。

---

## 二、核心改动点

### 2.1 基线表解析：移除硬编码校验

**原逻辑**（需删除）：
```python
expected_header = _EXPECTED_INCREMENTAL_HEADER  # 硬编码7列
if header != expected_header:
    normalized = _normalize_baseline_table_header(base_table)
    if normalized is not None:
        base_table = normalized
        base_md = _table_to_markdown(base_table)
    else:
        return {"ok": False, "error": "基线用例表头不符合规范..."}
```

**新逻辑**：
- 解析出基线表后，直接使用 `base_header = [str(c or "").strip() for c in base_table[0]]`
- 不再与 `_EXPECTED_INCREMENTAL_HEADER` 比较
- 删除对 `_normalize_baseline_table_header` 的依赖（或保留作为可选兼容，但不强制）
- 基线表为空或无法解析时，仍返回错误（保持「有基线才能补充」的前提）

### 2.2 基线表为空的前置校验

**维持**：`if not base_md` 时返回「基线用例表为空，无法做增量补充」。

（若产品后续允许「无基线纯补充」场景，可单独迭代；本期不做）

### 2.3 Prompt 构造：动态注入表头

**原逻辑**（需修改）：
```python
prompt.append("2. 输出格式必须为 Markdown 表格，表头严格为：| ID | 模块 | 测试项 | 优先级 | 前置条件 | 操作步骤 | 预期结果 |。")
```

**新逻辑**：
```python
header_str = " | ".join(base_header)
prompt.append(f"2. 输出格式必须为 Markdown 表格，表头严格为：| {header_str} |（列数和列名必须与基线表完全一致）。")
```

同时在「增量指令」相关描述中明确：
```python
prompt.append("=== 增量指令（用户补充需求，自然语言即可，无格式要求） ===")
```

### 2.4 增量输出校验：对比基线表头

**原逻辑**（需修改）：
```python
if delta_header != expected_header:
    return {"ok": False, "error": "增量用例表头不符合规范，预期为：ID | 模块 | ..."}
```

**新逻辑**：
```python
if delta_header != base_header:
    actual_str = " | ".join(delta_header)
    expected_str = " | ".join(base_header)
    return {
        "ok": False,
        "error": f"增量用例表头与基线不一致。实际：{actual_str}；基线：{expected_str}",
        ...
    }
```

### 2.5 ID 列索引与去重 key

**现状**：`_compute_next_id_from_table` 取首列（index 0）为 ID；去重 `_row_key` 使用 `vals[1], vals[2], vals[5]` 对应「模块、测试项、操作步骤」。

**调整**：
- ID 列：保持首列为 ID（与四Agent 9 列格式中「序号」或「用例编号」兼容，需确认主流水线 ID 所在列；若为第 2 列「用例编号」，则 `_compute_next_id_from_table` 需改为取第 2 列）
- 去重 key：改为**动态**根据 `base_header` 列数决定，例如：
  - 9 列：取列索引 2（主模块）、3（子模块）、7（测试步骤）等能表征用例唯一性的列
  - 7 列：取列索引 1、2、5
- 建议：根据 `base_header` 列名或位置，动态选择「模块类」「测试项类」「步骤类」列的索引，拼成 key；若实现成本高，可先按列数分支（如 `col_count >= 9` 用一套，`col_count == 7` 用另一套）

### 2.6 `_HEADER_ALIASES` 与 `_normalize_baseline_table_header`

- **可选保留**：用于将「用例编号」「主模块」等别名映射到规范列名，便于 `_compute_next_id_from_table` 和去重 key 的列索引解析。
- **本期建议**：若主流水线已固定为 9 列且列名稳定，可暂不依赖别名映射，直接按「首列 ID、第 2/3 列模块、第 7 列步骤」等固定索引处理 9 列格式；7 列格式另行分支。避免过度设计。

## 三、实施步骤（建议顺序）

| 步骤 | 内容 |
|------|------|
| 1 | 移除 `generate_incremental_cases` 中对 `_EXPECTED_INCREMENTAL_HEADER` 的硬编码校验，改为使用 `base_header` |
| 2 | 修改 Prompt 构造：`header_str = " \| ".join(base_header)`，表头规则动态注入 |
| 3 | 修改增量输出校验：`delta_header != base_header`，错误信息展示实际 vs 基线 |
| 4 | 调整去重 `_row_key`：支持 9 列格式的列索引（或按列数分支） |
| 5 | 确认 `_compute_next_id_from_table` 在 9 列格式下取正确的 ID 列（首列或「用例编号」列） |
| 6 | 联调测试：9 列基线 + 自然语言补充需求 → 增量生成 → 合并 → 导出 Excel |

---

## 四、回归影响

| 影响点 | 风险 | 说明 |
|--------|------|------|
| 7 列基线 | 低 | 若存在 7 列基线，`base_header` 自然为 7 列，逻辑兼容 |
| 合并逻辑 | 无 | `app_ui.py` 中合并仍按 `base_header`/`delta_header` 一致性校验，无需改动 |
| Excel 导出 | 无 | 导出逻辑与列数无关，按表格直接输出 |

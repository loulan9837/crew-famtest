# 用例补充·表头兼容与补充需求无格式限制 · 产品需求文档

> **文档用途**：修复「用例补充（增量生成）」报错「基线用例表头不符合规范」问题，并明确补充需求输入为自然语言无格式限制。
>
> **关联文档**：`用例补充-PRD.md`、`config/agents.yaml`、`四Agent提示词与任务编排-规格说明.md`

---

## 一、问题背景

### 1.1 用户报错

用户在使用「生成补充用例」时，收到错误提示：

```
基线用例表头不符合规范，预期为：ID | 模块 | 测试项 | 优先级 | 前置条件 | 操作步骤 | 预期结果
```

### 1.2 根因分析

| 现状 | 说明 |
|------|------|
| 四Agent主流水线产出 | 9列表格：`序号 \| 用例编号 \| 主模块 \| 子模块 \| 用例概述 \| 优先级 \| 前置条件 \| 测试步骤 \| 预期结果` |
| 用例补充模块校验逻辑 | 硬编码校验7列表头：`ID \| 模块 \| 测试项 \| 优先级 \| 前置条件 \| 操作步骤 \| 预期结果` |
| 结果 | 两套表头完全对不上，100% 报错 |

### 1.3 用户诉求

- **补充需求输入**：用户输入的是自然语言，可能只有几句话（如「新增断网场景」「修改XX位置的预期结果为弹窗提示」），**不应做任何格式限制**。
- **基线表头**：应**动态读取**当前基线用例表的实际表头，而非硬编码固定7列。

---

## 二、需求目标

| 目标 | 说明 |
|------|------|
| 基线表头动态适配 | 不再硬编码表头校验，改为读取基线用例表的实际列名与列数，支持9列、7列等多种格式 |
| 补充需求无格式限制 | Prompt 中明确「补充需求描述」为自然语言输入，几句话或描述更改位置均可，不做格式校验 |
| 增量输出与基线一致 | Agent 产出的增量用例表头必须与基线表完全一致（列数、列名、顺序） |
| 向后兼容 | 保持 ID 继承、去重、合并等现有逻辑不变 |

---

## 三、验收标准

| 编号 | 验收项 |
|------|--------|
| AC1 | 四Agent主流水线产出的9列用例表，作为基线时，用例补充不再报「基线用例表头不符合规范」 |
| AC2 | 补充说明/变更描述输入框：用户输入纯自然语言（如「新增支付超时3次重试的P0用例」），可正常触发生成 |
| AC3 | 增量 Agent 产出的用例表头与基线表完全一致（列名、列数、顺序），可正确合并 |
| AC4 | 7列格式的基线表（若存在）仍可正常工作 |
| AC5 | ID 继承、去重、合并至总用例库等既有逻辑保持不变 |
| AC6 | 错误提示语：当增量输出表头与基线不一致时，明确展示「实际」与「基线」差异，便于用户排查 |

---

## 四、非功能要求

- 不改变「用例补充」入口的展示条件（仍为有 `current_cases_df` 时展示）
- 不新增或删除 UI 组件
- 敏感信息、防御式编程等安全规范保持不变

## 〇、优化方向摘要（PM · 待审）

以下为拟定优化共识，后续各 Agent 的补充段落均**对齐以下方向**，不在本文另扩新规。

| 方向 | 说明 |
|------|------|
| **全回归用例** | 拆解与生成应对齐**全回归用例**所体现的能力覆盖与模块边界，避免只围着当期PRD片段展开导致过简。 |
| **整个项目** | 从**项目级**模块与链路审视当前需求，识别跨模块、跨能力的影响与回归面，而非单点功能自言自语。 |
| **非极端场景与简略问题** | 当前产出偏简略、考虑维度偏少；须**极端与非极端并重**——主路径、常见分支、回归防劣化等与极端边界同等需要展开，避免只剩极端个案或一句话带过。 |

**落地约束（不改变流水线前提）**：仍为四 Agent 接力；不改变表头列数与占位符链路；合并至 `agents.yaml` 时需与既有「排版红线」「优先级定义」并存且不冲突。

## 二、doubt_agent（1 号 · 文档分析师）— 建议追加

**对齐**：§〇 全回归视角、项目全局、非极端与极端并重。

```text
【深度与完备性（补充）】
- 除文档显性段落外，主动推演「未写但必须成立」的不变量：权限变更后可见范围、订单类操作的幂等与重复提交、跨页面返回后的缓存与刷新语义。
- 对每条核心流程至少追问一组对照：最小权限/最高权限、空数据与极大列表、主路径成功一次与连续重复操作。
- 若PRD出现枚举（状态A/B/C、入口X/Y），默认存在「非法组合或未定义跳转」，须在报告中点名缺口而非默认HappyPath唯一。
- 输出时仍为结构化风险条目，禁止因补充深度而改成散文或去掉必填字段。
```

---

## 三、organize_agent（2 号 · 测试点拆解）— 建议追加

**对齐**：§〇 全回归与项目模块边界、主路径/常见分支（非极端）与异常路径均衡。

```text
【测试点粒度与覆盖面（补充）】
- 「验证逻辑补充」必须写清：触发条件、关键中间状态、边界取值或网络/生命周期前提之一；禁止仅复述概述的同义词。
- 对PRD中同一控件的多规则（可见性、置灰、文案、次数限制），拆成独立测试点，禁止合并为一条笼统HappyPath。
- HappyPath与SadPath分量平衡：每个用户可见的新能力至少对应1条异常或兜底路径（权限拒绝、重复点击、超时、服务端错误占位），除非PRD明确声明不适用。
- 继承自风险报告的测试点在「验证逻辑补充」中必须写明与文档条款或状态的对应关系，避免只有标签无断言锚点。
```

## 四、case_agent（3 号 · 用例扩展）— 建议追加

**对齐**：§〇 纠正过简步骤与笼统预期；主路径与分支的可执行粒度（含非极端）。

```text
【步骤与断言深度（补充）】
- 严禁把2号「验证逻辑补充」中的多个独立断言挤进单行步骤或单行预期；应按观察顺序拆成多步，预期结果与步骤一一对应或可溯源编号。
- 测试步骤在遵守【角色】《页面》格式前提下，关键状态变更（登录态切换、列表刷新、弹层关闭）必须单独成步，禁止「一口气做完」式超长步骤。
- 预期结果须可判定：含界面可见结论或明确数据/文案片段；禁止「正常」「成功」等空洞表述。
- 若测试点隐含多终端或多角色协作，步骤中须体现角色切换或数据在不同端的可见性，不得默认为单人单机。
```

## 五、review_agent（4 号 · QA 验收）— 建议追加

**对齐**：§〇 防止相对全回归与大纲「系统性删减」；防仅保留极端或格式过关即可。

```text
【防「过简用例」验收（补充）】
- 除既有四条红线外，对明显「一步覆盖多点断言」「预期结果过于笼统」的行判定为Fail，要求3号拆步或拆行（在修改建议中写清如何拆）。
- 对照2号大纲做抽样核对：高风险模块下测试点数量与表格行数不应出现系统性腰斩；若大量省略须判为覆盖不足而非仅格式问题。
- 允许在不影响表头与优先级分布约束的前提下，建议合并真正重复的凑数行；但不得以「精简」为由删掉SadPath或继承自风险条的异常场景。
```

## 六、是否同步改 Task 描述（可选，仍待审）

若身份补强后仍偏「执行层面偏弱」，可考虑仅在 `tasks[].description` **增收一句**（不改变占位符与链路），例如：

- **task3**：强调「逐条展开2号大纲，不得省略测试点ID对应关系」。
- **task4**：强调「对步骤粒度与断言可判定性按补充规则抽检全表」。

此项独立决策：**只改 description 也属于提示词变更**，与 `backstory` 合并前建议一并评审。

# 用例对话（Agent交互式用例补充与修改）· 产品需求文档

> **文档用途**：新增一个独立入口，让用户通过多轮对话与Agent协同完成测试用例的逐条补充、修改与优化，弥补批量增量生成在精细化调整场景中的不足。
>
> **关联文档**：`用例补充-PRD.md`、`四Agent提示词与任务编排-规格说明.md`、`.cursor/rules/project-standards.mdc`、`项目流程总览.md`

---

## 一、背景与目标

### 1.1 背景

- **现状**：
  - 平台已具备「四Agent流水线」一键生成整张用例表的能力；
  - 已具备「用例补充（增量生成）」批量产出Delta用例的能力。
- **未覆盖场景**：
  - 用户需要**逐条**讨论某个场景的用例补充或修改（如"这条超时用例的预期结果需要改成弹窗提示"）；
  - 用户想让Agent**解释**为什么需要某个极端场景的用例，或请求Agent**从安全/性能角度**补充遗漏；
  - 用户针对同一需求可能产生**多轮**讨论（第一轮补充断网场景 → 第二轮追加并发场景 → 第三轮修正预期结果措辞），当前架构不支持对话上下文延续；
  - 对话历史不持久化，刷新即丢失，无法回顾与复用。

### 1.2 目标

| 目标 | 说明 |
|------|------|
| 独立入口 | 新增「用例对话」顶层模块Tab，与「生成用例」「文档问答」并列，专用于围绕测试用例展开的Agent交互 |
| 多轮对话 | 支持用户与Agent进行多轮对话，Agent在每轮中理解完整上下文（原始需求 + 现有用例 + 项目记忆 + 本轮对话历史），逐步完善用例 |
| 对话持久化 | 对话会话持久化到本地（优先 SQLite，极端环境降级 JSON），刷新页面不丢失，可随时恢复 |
| 历史管理 | 显示历史对话列表（按时间倒序），支持搜索、恢复、删除（二次确认） |
| Agent输出可操作 | Agent产出的用例建议以标准Markdown表格输出时，用户可直接预览；后续可扩展一键合入能力 |

### 1.3 与现有模块的边界划分

| 模块 | 定位 | 核心差异 |
|------|------|---------|
| 生成用例 | 一键批量生成整张用例表 | 全量流水线，非交互式 |
| 用例补充（增量生成） | 基于变更描述批量产出Delta用例 | 单轮提交，只输出Delta表格 |
| 文档问答 | 基于需求文档的通用问答 | 不聚焦用例、不绑定用例上下文 |
| **用例对话（本需求）** | **围绕特定需求的用例做多轮对话式补充/修改/评审** | **多轮上下文延续、绑定用例快照、对话持久化** |

## 二、用户场景与交互流程

### 2.1 使用场景枚举

| 场景 | 用户典型输入 | Agent期望行为 |
|------|-------------|-------------|
| 逐条补充 | "针对支付超时场景，补充一条P0用例" | 产出单条标准格式用例，ID从现有最大值+1开始 |
| 修改预期结果 | "ACT-003的预期结果改成弹出错误提示并自动退出登录" | 输出修改后的完整用例行（标注"修改建议"） |
| 覆盖度分析 | "从安全测试角度看，当前用例还缺少哪些场景" | 列出缺失场景清单，逐条附带建议的用例内容 |
| 解释与论证 | "为什么需要断网恢复后重新鉴权的用例" | 从业务逻辑角度解释风险点和必要性 |
| 批量优化 | "把所有P2用例的操作步骤精简到3步以内" | 输出修改后的用例表片段，保持表头一致 |
| 回归风险 | "新增的自动登出逻辑会影响哪些现有用例" | 分析影响范围，产出回归验证用例 |

### 2.2 用户操作路径

```
┌─────────────────────────────────────────────────────┐
│  1. 进入「用例对话」Tab                               │
│     ↓                                               │
│  2. 选择对话来源：                                    │
│     ├─ [新建对话] → 选择需求来源                      │
│     │   ├─ 从历史生成记录中选择（自动绑定PRD+用例）    │
│     │   └─ 手动粘贴需求+用例                         │
│     └─ [恢复历史对话] → 从下拉列表选择                │
│     ↓                                               │
│  3. 对话区域（st.chat_message + st.chat_input）      │
│     ├─ 用户发消息 → Agent回复                        │
│     ├─ 快捷指令按钮：                                │
│     │   ├─ "分析用例覆盖度"                          │
│     │   ├─ "补充极端场景用例"                         │
│     │   └─ "检查预期结果规范性"                       │
│     └─ 多轮持续对话                                  │
│     ↓                                               │
│  4. 对话管理：                                       │
│     ├─ 自动保存（每次发送/接收消息时持久化）           │
│     ├─ 删除当前对话                                  │
│     └─ 搜索历史对话                                  │
└─────────────────────────────────────────────────────┘
```

### 2.3 新建对话详细流程

1. **选择需求来源**
   - **从历史生成记录选择**：
     - 渲染`st.selectbox`展示`run_history`中的记录（标题+时间）；
     - 选中后自动加载该记录的PRD全文（`result_str`或`txt_path`中恢复）作为`prd_context`；
     - 同时读取该记录关联的用例Markdown作为`cases_context`。
   - **手动粘贴**：
     - 提供两个`st.text_area`：一个用于粘贴需求文档，一个用于粘贴现有用例（可选）；
     - 适用于外部带入的需求或未通过本平台生成的用例。

2. **自动创建对话记录**
   - 用户发送第一条消息时，系统自动创建对话记录并持久化；
   - 对话标题自动取自需求文档大标题或用户第一条消息的前30字。

### 2.4 恢复历史对话

- 在模块顶部提供`st.selectbox`，列出历史对话列表（按`updated_at`倒序）；
- 格式：`{title} · {message_count}条消息 · {updated_at}`；
- 选中后恢复完整对话记录（包括绑定的PRD和用例快照），继续对话。

### 2.5 删除对话

- 每条历史对话旁提供「删除」按钮；
- 点击后进入二次确认态（显示"确认删除？"按钮），再次点击才执行删除；
- 删除后自动刷新列表。

## 三、数据结构与持久化

### 3.1 对话记录JSON Schema

```json
{
  "id": "conv_20260302_143000_a1b2",
  "title": "支付模块超时场景用例讨论",
  "run_record_id": "20260302_130000",
  "prd_snapshot": "PRD原文完整内容...",
  "cases_snapshot_md": "现有用例表Markdown完整快照...",
  "messages": [
    {
      "role": "user",
      "content": "针对支付超时场景，补充几个P0级别的异常用例",
      "timestamp": "2026-03-02 14:30:05"
    },
    {
      "role": "assistant",
      "content": "基于当前用例表分析...\n\n| ID | 模块 | ...",
      "timestamp": "2026-03-02 14:30:28"
    }
  ],
  "created_at": "2026-03-02 14:30",
  "updated_at": "2026-03-02 15:20",
  "project_id": "FAMBASE"
}
```

### 3.2 存储位置与后端

- **主后端：SQLite**。在现有 `memory_store` 所依赖的 SQLite 中新建 `conversations` 与 `messages` 两张表，利用数据库原生的行级锁解决并发安全；与 Fam 项目已有的 `memory_store` 双端降级设计保持一致。
- **降级后端**：仅在极端云端无 SQLite 环境下，降级使用 `output/case_conversations.json`（`{"items": [...]}`）；写入时采用 `write → rename` 原子替换，降低损坏风险。
- **最大记录数**：50条（超出后删除最旧的对话）

### 3.3 关键状态（st.session_state）

| 字段 | 类型 | 说明 |
|------|------|------|
| `case_chat_current_conv_id` | str \| None | 当前活跃的对话ID，None表示尚未建立对话 |
| `case_chat_messages` | list[dict] | 当前对话的消息列表（与JSON中的messages同步） |
| `case_chat_prd_context` | str | 当前对话绑定的需求文档内容 |
| `case_chat_cases_context` | str | 当前对话绑定的用例快照内容 |
| `case_chat_delete_confirm_id` | str \| None | 二次确认删除的对话ID |

### 3.4 状态流转

```
[无对话] ──发送第一条消息──→ [对话中] ──持续消息──→ [对话中]
    ↑                          │
    │        ┌─────────────────┤
    │        │                 │
    │   [结束对话]         [恢复历史对话]
    │   = 保存并归档           │
    │   对话记录保留在历史中     │
    │        │                 │
    └────────┘                 │
    ↑                          │
    └──────────────────────────┘

[无对话] ──恢复历史对话──→ [对话中]
```

> **核心原则**：「结束当前对话」= **保存并归档**，对话记录永久保留在历史列表中，用户随时可恢复继续。
> 对话记录只有两种途径会被真正删除：
> 1. **手动删除**：用户在历史列表中点击「删除」并二次确认；
> 2. **超限淘汰**：对话总数超过上限（50条）时，自动删除`updated_at`最早的一条。

## 四、Agent角色与Prompt设计

### 4.1 角色定义

> 「用例对话Agent」不走四Agent流水线，也不走增量生成链路，而是一个**独立的、专精于用例讨论的交互式Agent**。

- **角色名**：测试用例顾问（Test Case Advisor）
- **职责**：围绕特定需求的测试用例展开多轮对话，包括但不限于：补充、修改、解释、覆盖度分析、回归风险评估。
- **底层模型**：复用用户在「设置」中配置的Gemini模型和Key。

### 4.2 System Prompt结构

```
你是一位资深的测试用例顾问，拥有丰富的测试开发经验。

你当前的工作上下文：
1. 【需求文档】：{prd_snapshot}
2. 【现有用例表】：{cases_snapshot_md}
3. 【项目记忆】：{project_context}（如有）

你的职责是围绕上述需求和用例，与用户展开多轮对话，协助完成以下任务：
- 补充遗漏的测试场景（必须覆盖极端场景：断网、杀进程、边界值）
- 修改现有用例的任意字段（ID、模块、预期结果等）
- 分析当前用例覆盖度并指出薄弱环节
- 评估新逻辑对既有用例的回归风险
- 解释特定用例的设计依据

产出规范（输出用例时必须遵守）：
- 表头固定：ID | 模块 | 测试项 | 优先级 | 前置条件 | 操作步骤 | 预期结果
- 中英/数字边界不得出现空格
- 预期结果绝对去动词化
- 新增用例ID从当前最大ID+1开始
- 修改用例时保留原始ID

表格输出物理隔离（关键，用于后续一键合入）：
- 当你的回复中包含具体的测试用例表格时，必须且只能将表格放置在独立的 XML 标签 <case_table> 和 </case_table> 内部
- 解释性文字、分析思路等必须写在标签外部

回复风格：
- 先简要说明分析思路（2-3句）
- 再给出具体用例表格或修改建议
- 如发现用户的修改请求与现有逻辑冲突，必须主动提醒
```

### 4.3 上下文窗口管理（废除硬截断）

- **PRD 与用例快照**：完整传入，不再进行字符数硬截断。Gemini 1.5 Pro 等模型具备 100 万～200 万 Token 超长上下文，物理截断会导致后半部分业务逻辑丢失，引发幻觉。
- **Context Caching（推荐）**：将庞大的 PRD 和全量用例作为 Cached Content 挂载，每次对话只消耗极少新增 Token，同时降低 API 成本和响应延迟；实现时优先支持 Gemini Context Caching。
- **对话历史**：最近 20 条消息（滑动窗口），仅用于控制单次请求体规模；若启用 Context Caching，可适度放宽。
- **项目记忆**：可选注入，按需截断（如 5000 字符）以控制单次请求 Token。

### 4.4 快捷指令（动态变量注入）

快捷指令**不能是纯静态字符串**，必须在 UI 层做动态变量注入，避免 Agent 不知道当前主表最大 ID 而擅自从 FAM-001 重新编号或引发 ID 冲突。

| 快捷按钮文案 | 自动发送的消息（含动态注入） |
|-------------|---------------------------|
| 分析用例覆盖度 | "请分析当前用例表的覆盖度，指出遗漏的功能点和极端场景" |
| 补充极端场景 | 若 `cases_snapshot_md` 可解析出最大 ID（如 FAM-015），则发送："请针对当前需求，补充断网恢复、杀进程重启、边界值极限等极端场景的测试用例。**注意：新增用例的 ID 必须严格从 FAM-016 开始递增。**"；若无则可注入占位提示 |
| 检查预期结果规范 | "请检查现有用例表中所有预期结果的规范性：是否含有动词、是否需要编号、格式是否统一" |
| 回归风险评估 | 同上，若可解析最大 ID，则追加："新增用例的 ID 必须从 {next_id} 开始递增。" |

**实现要求**：底层 Python 在用户点击快捷指令时，从 `cases_snapshot_md` 解析当前最大用例 ID，拼接到发送给 Agent 的 Prompt 中。

## 五、历史对话管理

### 5.1 历史列表展示

- 位于模块顶部，使用`st.expander("对话历史", expanded=False)`包裹
- 列表项格式：

```
📝 {title}
   {message_count}条消息 · 最后更新：{updated_at} · 项目：{project_id}
   [恢复对话] [删除]
```

- 支持关键字搜索（按标题模糊匹配）

### 5.2 结束对话（归档，非删除）

- 用户点击「结束当前对话」时，**对话记录原样保留在历史列表中**，仅清空当前工作区回到初始态
- 用户随时可从历史列表中恢复该对话继续讨论
- **结束 ≠ 删除**，这是本功能的核心设计原则

### 5.3 删除机制（仅两种途径）

对话记录只有以下两种方式会被真正从存储中移除：

| 途径 | 触发条件 | 行为 |
|------|---------|------|
| 手动删除 | 用户在历史列表中点击「删除」→ 二次确认「确认删除？」 | 从存储（SQLite/JSON）中移除该条记录并刷新 UI；若删除的恰好是当前活跃对话，同时清空对话区域回到初始态 |
| 超限自动淘汰 | 新建对话时，若对话总数 ≥ 50条上限 | 自动从存储中删除 `updated_at` 最早的一条，为新对话腾出空间；不影响当前活跃对话 |

### 5.4 自动保存

- **触发时机**：每次用户发送消息 + Agent回复完成后，自动将当前对话状态写入存储（SQLite 或 JSON 降级）
- **结束对话时也触发一次保存**，确保最后一轮对话内容完整持久化
- **防御**：SQLite 使用行级锁避免并发覆盖；JSON 降级时采用 `write → rename` 原子替换，写入前校验路径在允许目录内（`_ensure_output_in_allowed_dir`）

## 六、架构级风险与防御

### 6.1 风险1：对话上下文超出Token上限

- **隐患**：PRD + 用例 + 20条对话历史可能超过模型上下文窗口
- **防御**：
  - **废除 PRD/用例字符数硬截断**，完整传入（Gemini 1.5 Pro 等具备超长上下文）
  - 优先使用 **Gemini Context Caching**，将 PRD 与用例作为 Cached Content 挂载
  - 对话历史使用滑动窗口（最近 20 条）
  - 超限时自动截断最早的对话，并在首条消息前追加 "[历史对话已截断]" 提示

### 6.2 风险2：Agent回复格式不稳定与未来合入

- **隐患**：对话式交互中 Agent 可能混合自然语言和表格，未来做「一键合入基线」时正则提取易崩溃
- **防御**：
  - System Prompt 中**强制**：当回复包含测试用例表格时，必须且只能将表格放在 `<case_table>` 与 `</case_table>` 内部；解释性文字写在标签外
  - UI 层用 `st.markdown` 渲染全部内容；底层可通过标签精准截取表格，为「一键合入」留下安全提取锚点
  - 不强制解析表格（区别于增量生成），允许 Agent 自由回复，但表格必须受标签约束

### 6.3 风险3：并发写入与存储损坏

- **隐患**：纯 JSON 文件在 Streamlit 多 Tab / 疯狂点击下易发生文件锁冲突或数据被覆盖清空
- **防御**：
  - **主存储为 SQLite**：新建 `conversations` 与 `messages` 表，利用数据库行级锁解决并发
  - **降级为 JSON**：仅在无 SQLite 环境使用；写入时 `write → rename` 原子替换
  - 读取时 `try-except` 兜底，损坏时返回空列表而非崩溃

### 6.4 风险4：历史对话中的用例快照过期

- **隐患**：恢复历史对话时，绑定的用例快照可能已不是最新版本
- **防御**：
  - 恢复对话时在顶部提示"此对话的用例快照来自{created_at}，可能与最新版本不同"
  - 提供「刷新用例上下文」按钮，可手动更新为最新版本
